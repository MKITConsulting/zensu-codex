# Codex port status

This document records how the native Codex plugin relates to upstream Zensu: what
the Codex host does, which Zensu function is taken over, which one is rebuilt
natively, and which one is excluded, each with its reason. Phase 0 fills the host
section below. Later phases add the per-function status.

## Phase 0: what the Codex host does

Every statement in this section comes from the host probe in
`evals/host-hook-contract/`, run against the real Codex binary with a local mock
model, a throwaway `HOME` and a throwaway `CODEX_HOME`. The probe needs no
credentials. It points every HTTP(S) and ALL proxy variable at a closed loopback
port, because on 0.157.1 an unisolated run showed Codex cloning its curated plugin
marketplace from `https://github.com/openai/plugins.git` in a background `git`
process that outlived Codex. The recorded results are machine-written:

- `evals/host-hook-contract/results/0.157.1.json` (the installed version when phase 0
  started)
- `evals/host-hook-contract/results/0.163.0.json` (the newest release when phase 0
  started; 0.164.0 has been released since and is not measured)
- `evals/host-hook-contract/results/0.166.0.json` (the installed version on
  2026-11-01, the first recording with the plugin-update scenario)

Every question row below ends in a hidden `facts` comment that names the recorded
facts it rests on, as `path=value` pairs. CI resolves each pair in every results
file, or only in the named version's file for a `facts@<version>` comment, and
fails when a row has no citation or a cited value differs from the recording.

Re-measure after any Codex upgrade:

```bash
bash evals/host-hook-contract/run-probe.sh --check
bash evals/host-hook-contract/run-probe.sh --codex <path to another codex> --check
```

`--check` runs all 70 scenarios and exits non-zero when the measured contract
drifts from the recorded one. The embedded hook schemas live next to the results
in `evals/host-hook-contract/schemas/<version>/`. `schemas/0.144.1/` comes from
the earlier phase1 branch and has no recorded results.

### Conditions

- **Surfaces.** The probe measures three tool surfaces, and every statement below
  holds only for the surfaces it names.
  - The *classic* surface: an unknown model slug (`probe-model`) gets plain
    function tools, among them `exec_command`, `write_stdin`, the
    `multi_agent_v1` spawn tools and `request_user_input`, but no `apply_patch`.
  - *Code mode*: `gpt-6-sol` gets one JavaScript `exec` tool that nests the
    others, `apply_patch` included, next to the `collaboration` spawn tools.
  - *gpt-5.5*: the one model of the bundled catalog not marked
    `tool_mode: code_mode_only` gets plain function tools with a freeform
    `apply_patch`, and no multi-agent tools at all.

  Every other catalog model is code-mode only, so most users get code mode.
- **Coverage.**
  - On all three surfaces: the offered tools, the `exec_command` payload and its
    PostToolUse `tool_response` type, a JSON `Bash` deny and a Stop
    `decision: "block"`.
  - On the classic surface and in code mode: the other deny and Stop shapes,
    `write_stdin`, subagents and their tool calls, a deny inside a subagent, a
    spawn deny, SubagentStop blocks and holds, agent role discovery and the
    read-only role sandbox, and `request_user_input`.
  - In code mode and on gpt-5.5: the `apply_patch` payload and its JSON deny.
  - In code mode only: the exit-2 `apply_patch` deny, a multi-file patch, the
    `apply_patch` and spawn denies inside a subagent, the reviewer tool profile
    and its nesting, the roles of an untrusted project, the workspace-write
    parent, and a subagent's messages to the root thread.
  - On the classic surface only: compaction, PermissionRequest, interrupt, hook
    trust, a plugin update under an open thread, plan approval, and the deny and Stop block of trusted hooks without
    the trust bypass.
- **Settings.** Unless a scenario overrides it, `config.toml` sets
  `approval_policy = "never"`, `sandbox_mode = "danger-full-access"` and
  `[features] hooks = true` and `plugins = true`. Every `codex exec` run passes
  `--dangerously-bypass-hook-trust`, except the untrusted run and the three late
  runs that measure trusted hooks after the probe granted trust in `config.toml`.
  App-server runs measure trust first and then grant it through
  `config/batchWrite`. Each results file lists every override under `conditions`.

### Corrections to the master plan

- The plan expected `request_user_input` in the main thread outside `codex exec`. Measured: it works only in Plan mode, on the classic surface and in code mode.

### Residual gaps

- A model shell's environment is model-controlled. A command can set any `CODEX_*` or `ZENSU_*` variable a helper reads, so a helper can never prove which thread started it; only the hook payload of that command can.
- A PreToolUse gate on command text does not keep a shell-capable subagent away from Session Control: `write_stdin` into a `tty: true` shell fires no hook, and an encoded or scripted command passes any text match. Session Control state therefore changes only in hook processes acting on a main-thread payload, and it is out of a model shell's reach only where the sandbox keeps the shell from writing it. Not measured: whether Codex runs hook processes outside the model sandbox, and which paths outside the project a subagent under a `workspace-write` parent can write. Under `danger-full-access` a subagent shell can write that state directly, and nothing in the plugin stops it.
- `write_stdin` is unhooked, and a `tty: true` call reaches PreToolUse with only `{command}`, so an interactive process cannot be policed after it starts.
- Plan mode is visible to hooks only through the approval prompt text that a client chooses to send. Any client counts, also one that a model shell starts, nested or resuming the root thread; whether such a client reaches the root thread, and what its UserPromptSubmit carries, is not measured.
- Untrusted hooks fail silently in the app server and in `codex exec`. Only a trust check such as the doctor's, or a client that reads `hooks/list`, can surface it.
- Plugin hooks without a `[features]` table were measured in one `codex exec` run with the trust bypass; a trusted run without the bypass and without the table is not measured (a late trusted run that drops the table would close it).
- `agent_type` is the role name alone, and the spawn gate's shadow check sees only a project role in `.codex/agents/` that takes a Zensu reviewer's name. Sources it does not see, each unmeasured: a `[agents.<name>]` table in a project `config.toml` (a probe project with that table would close it); whether Codex takes a role's name from its file name or from its `name` field, because every probe role uses the same name for both (a role whose two names differ would close it); and a `.codex` directory in a parent of the project, which no probe project has (a nested probe project would close it). A positive check of the loaded role would cover all of them, but only one that rests on no secret: a token the validator demands in the final message reaches the parent with the first accepted review. The digest check in the agent-role row rests on one unmeasured fact, whether the reviewer's own transcript, which SubagentStop `agent_transcript_path` names, records the role's developer instructions (a probe that reads that transcript at SubagentStop would close it).
- A subagent's hooks do not name its spawner; only its SubagentStop `transcript_path` does. A deny keyed on ancestry is impossible at PreToolUse, which is why the reviewer deny stops delegation at the reviewer's own spawn.
- A deny inside a subagent was measured for `Bash`, `apply_patch` and spawning only. The other tools a reviewer keeps that fire PreToolUse rely on the same deny rule without a measurement.
- Every subagent measurement ran in `codex exec` with the trust bypass, and none ran in the app server: the deny inside a subagent, the spawn deny, the SubagentStart and SubagentStop payloads and the SubagentStop hold. With trusted hooks and no bypass only the root thread's `Bash` deny and Stop block were measured, so whether trusted hooks gate a subagent the same way is not measured (late trusted runs of the subagent deny, the spawn deny and the SubagentStop hold, and an app-server spawn on a trusted thread, would close it).
- In code mode a reviewer keeps the outer `exec` tool, which fires no PreToolUse, so no deny reaches what it runs. Its JavaScript runtime is not measured: whether `require`, `process`, `fetch` or a dynamic `import` exist there, and whether it can read or write a project file. Until phase 2 measures that, a code-mode reviewer is not confined by the deny rule.
- Of the messages a subagent can send, only a code-mode subagent's `send_message` and `followup_task` to the root were measured; the classic `send_input` was not.
- A subagent's message to an idle root thread is not measured: the one measurement sent it while the root turn was running in `codex exec` and waiting on the subagent. Whether such a message starts a root turn, and whether that turn fires a root UserPromptSubmit that carries the message, decides whether a subagent can fake a plan approval (an app-server scenario whose root turn ends before the subagent messages `/root` would close it).
- gpt-5.5 offers no multi-agent tools, so no reviewer can be spawned there, and its `request_user_input` behavior is not measured.
- Only six matchers were tested, so which matcher catches the code-mode spawn names is open. No decision depends on it, because the dispatcher routes by `tool_name`.
- The role sandbox and the tool profile were measured with `approval_policy = "never"` only.
- On 0.166.0 the hook-trust sequence bumps the plugin version with every edit, so it does not tell a content edit from a version bump: whether an edited script or `hooks.json` entry without a new version also turns the hooks `modified` is not measured (a step that edits without bumping the version would close it).
- The plugin update was measured through the app server's `plugin/install`, on a thread the probe loaded itself and between two turns, and the hooks were trusted again through `config/batchWrite` with a reload of the user config. An update through the TUI's `/plugins` or the desktop app, a re-trust in the `/hooks` dialog while a thread is loaded, and an update while a turn is running are not measured.
- Codex releases between 0.163.0 and 0.166.0, and after 0.166.0, are not measured.
